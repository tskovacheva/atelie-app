# Глина

**Малко приложение за керамично ателие.** По-близък дневник, отколкото инструмент — за рецепти на глазури, материали, експериментални тестове и живота на изделията от мокра глина до финал.

> Направено за собствена употреба в ателие, не за общ продукт.

## Какво прави

Шест раздела, които покриват цикъла на ръчната керамика:

- **Изделия** — каталог на парчетата с типове (ваза, чаша, музикален инструмент...), снимки, свързани глини и глазури, две температури (бисквит + глазурно), и **Процес** — timeline на стъпките от изработката (етапи, изпичания, декорации, прогрес)
- **Рецепти** — глазурни рецепти със съставки и проценти, температура/конус, тип, препоръчан профил на изпичане, калкулатор за грамове при произволен батч
- **Материали** — девет таба: глини, базови суровини, оксиди/оцветители, готови глазури, ангоби, подглазурни бои, **суровини** (дива глина), **маси** (собствени замеси), wishlist. Склад с известия за ниски запаси, химичен анализ, цена за единица
- **Тестове** — дневник на глазурни опити (от рецепта или готова глазура) с оценка, дефекти, резултатни полета, снимки. Приспада съставките от склада при създаване
- **Изпичания** — профили с ramp rates и задръжка; свързани с тестове, рецепти и изпичания в Процеса
- **Библиотека** — лична база знания с предзаредени справочни материали; backup/restore; „Място на устройството"

Всеки раздел поддържа търсене, филтри, сортиране (азбучно по default) и дублиране на записи. Между тях има **свързани записи** (derived relations) — от рецепта виждаш свързаните изделия и тестове, от профил виждаш кои тестове и рецепти го ползват, от материал виждаш в кои рецепти, изделия и тестове се използва.

### Процес — timeline на изделието

Всяко изделие може да има **Процес** — хронологичен запис на стъпките от изработката:

- **Етап** — преход между състояния (Сурово → Кожна влажност → Сухо → Бисквит → Глазирано → Готово)
- **Изпичане** — 13 метода: електрическа, газова, дървена, раку, чушкопек, pit, barrel, сагар, стърготини, сода, солно, обвара, друго. Атмосфера: окислително / редукционно
- **Декорация** — сграфито, ангоба, тера сигилата, подглазурни бои, глазура, печат, полиране и още (12 техники), със свързани материали
- **Прогрес** — междинна снимка/бележка без промяна на статуса

Декорациите и прогресът носят опционално поле **„на етап"** — една и съща техника значи различно нещо при кожна влажност и при сухо.

Процесът е **опционален**. Можеш да създадеш изделие само на финален етап (без история) или да документираш всяка стъпка с дата, бележка и снимки.

Подробна спецификация на event типовете е в [`EVENT_SCHEMA.md`](EVENT_SCHEMA.md).

### Суровина и Маса

От v1.6–v1.7 приложението документира и **пътя на материала**, не само на изделието.

**Суровина** (дива глина) — партида, извадена от конкретно място. Носи локация, координати, дата, начално сухо тегло, геоложки бележки — и **процесна биография**: добиване, диагностика (оцетен тест), промивки (с ppm преди/след, съотношение, утаяване), пресяване (mesh, тегло), отлежаване.

**Маса** — материал, който знае от какво е направен. Компоненти с проценти, дата на замесване, дата на готовност. Компонент може да е суровина, търговски материал, оксид, ангоба, рецепта — или друга маса.

Суровината **не се избира директно** при изделие или тест. За да я ползваш, правиш маса от нея (100% ако е без добавки). Причината: същата партида може да влезе в няколко различни тела — не може едновременно да е и чистата версия, и версията с шамот.

Разделението е:
- **Рецепти** — смеси, които *нанасяш* (глазури)
- **Маси** — смеси, които *формуваш* (тела)

## За кого е

Ателие-базирана керамична практика, не търговски поточен процес. Ако правиш серийно производство, продаваш партиди или водиш клиенти — това не е продуктът за теб.

## Как работи

- **Single-file PWA** — един HTML файл, `sw.js`, manifest, икони. Без build step.
- **Без backend, без акаунти.** Всички данни се пазят локално на устройството.
- **Работи офлайн** благодарение на service worker.
- **Инсталира се като app** на телефон или десктоп (Add to Home Screen / Install App).
- **Photo compression** — снимките се компресират до 800px JPEG (quality 0.75).
- **Backup/restore през JSON** — в раздел Библиотека, долу. Препоръчителен workflow: експорт след всяка сесия, с дата и устройство в името.

## Технически детайли

- Vanilla JavaScript, inline CSS, inline HTML. Без framework-и, без dependencies.
- Около 5500 реда. Оптимизирано за четливост, не за производителност.
- **Storage: IndexedDB** (от v1.5.0) под ключ `atelie_idb`; библиотеката отделно под `atelie_userlib`. localStorage се пише още като backup mirror — предстои премахване.
- **Sync wrapper над async store** — in-memory кеш (`_storageCache`) се пълни при boot от `bootStorage()`; четенето е синхронно от кеша, писането — async към IndexedDB. Така `safeLoadJSON` / `safeSaveJSON` запазват синхронния си интерфейс без пълен async refactor.
- Data structure: `{pieces, recipes, materials, tests, firingProfiles, _migrations}` — всичко масиви.
- Derived relations — никакви reverse foreign keys не се пазят; всички „свързани" списъци се изчисляват при отваряне на detail екран.
- **Event-based piece model** (от v1.4.0) — `piece.events[]` съхранява хронологична история. Backward-compatible: piece-ове без events работят с flat полета.
- Cross-entity референции са префиксирани стрингове: `mat:<id>`, `rec:<id>`, резолвени от `_resolveMaterialRef()`.
- Service worker cache strategy: navigation → network-first, assets → cache-first. `CACHE_NAME` се bump-ва при всеки deploy. SW праща `SW_UPDATED` съобщение → toast за обнова.
- **Android back button** — History API integration; back затваря modal/detail вместо да затвори PWA-то.
- Design system от v1.2.0: sage + terra cotta палитра, Tenor Sans + Jost шрифтове. Стари CSS variables запазени като aliases.
- **Migration system** — `runMigrations()` при load с idempotent flag-ове в `DB._migrations` и safety backup-и.

## Запазване на данни — важно

- **Данните са само на това устройство.** Ако работиш на телефон и лаптоп — правиш експорт и импорт ръчно.
- **PWA и browser имат отделен storage** на Android/iOS — не смесвай двата за преглед на същите данни. Избери един и работи в него.
- **При деинсталиране на PWA** може да се изтрият данните (зависи от OS). Винаги експортвай преди reinstall.
- **Между устройства** няма автоматична синхронизация. Workflow: експорт от A → качване в облак → сваляне на B → импорт.
- **Backup файлове** съдържат timestamp + device в името (напр. `atelie_2026-07-16_1435_mobile.json`).
- **„Място на устройството"** в Библиотеката показва заетото място, свободното (много/средно/малко), разбивка по вид данни, и два cleanup-а: премахване на стари migration snapshot-и и намаляване на едри снимки.

## Deploy

Върху GitHub Pages. Пет файла за production:

```
index.html
sw.js
app.webmanifest
icons/icon-192.png
icons/icon-512.png
```

`ROADMAP.md`, `EVENT_SCHEMA.md`, `FUNCTIONAL_SPEC.md`, `UX_BRIEF.md` и `README.md` живеят в repo-то, но не се сервират директно на потребители.

При всеки production update:
1. Експорт на backup от приложението
2. Bump `APP_VERSION` в `index.html`
3. Bump `CACHE_NAME` в `sw.js`
4. Commit + push → GitHub Pages deploys автоматично
5. Провери версията в Chrome browser на целевия URL (не в PWA), за да се увериш, че deploy-ът е преминал
6. Отвори PWA-то → toast за обнова → reload

**Внимание при Android PWA:** Android Chrome понякога закотвя стар service worker cache. Ако новата версия не се появява след рестарт, използвай nuclear reset (Chrome Settings → Site settings → Clear data за домейна). Винаги експортвай backup първо.

## Принципи

- **Малки patch-ове.** Инкрементални промени без refactor.
- **Backward compatibility.** Всеки patch трябва да работи със стари данни.
- **Safe guards навсякъде.** Null checks, `|| ''` fallbacks, optional chaining за липсващи полета в стари records.
- **Derived, не дублирано.** Свързаните записи се изчисляват, не се пазят.
- **Без външни dependencies.** Един file, без build tooling.
- **UX над features.** Ако feature не решава реална ежедневна болка, не се добавя.
- **Тествай между фази.** Без real-world употреба не се знае дали основата е стабилна.
- **Винаги deploy-аеми междинни версии.** Всяка фаза разделена на 3-5 малки версии, всяка функционална самостоятелно.
- **Two-phase removal.** Миграция в една версия, премахване на legacy code в следващата.
- **Валидация преди deploy.** JS синтаксис + проверка, че всеки `getElementById` има съответен елемент в HTML-а. Второто хвана реален бъг във v1.6.0, който синтактичната проверка пропусна.
